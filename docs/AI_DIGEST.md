# PolyCraft - AI Context Digest

## 0. Model & Harness Configuration
Two machines are involved and **their limits must not be transferred between them**. The *inference host* runs the model and the harness; the *dev host* runs VS Code, the agent extension, and PolyCraft itself. This file is written to be pasted whole into one prompt.
- **Inference host (runs the model):** 12 GB VRAM, 96 GB DDR5. Model: Qwen3-Coder-30B-A3B-Instruct, `Q4_K_M` - 30.5B parameters, 3.3B active per token, 48 layers, 262,144 native context. The 18.56 GB file exceeds 12 GB of VRAM, so layers split across GPU and system RAM: `--n-gpu-layers 12 --flash-attn --ctx-size 131072 --parallel 1 --cache-type-k q8_0 --cache-type-v q8_0 --jinja --mlock --threads <physical cores> --keep 12000 --cache-reuse 256`.
- **Sizing math:** grouped-query attention gives 4 KV heads at `head_dim` 128 over 48 layers, so the KV cache is 2 x 4 x 128 x 48 x 2 bytes = **96 KiB per context token** in FP16, 51 KiB at `q8_0` - 6.0 GiB at 128k, 3.2 GiB at 65k. **The cache follows the layer split**, so at `--n-gpu-layers 12` only 12/48 of it is in VRAM: about 1.5 GiB at 128k, the rest in system RAM. Each layer is 17.28 GiB / 48 = **0.36 GiB**, so twelve layers (4.3 GiB) plus 1.5 GiB of KV plus roughly 1.2 GiB of compute buffers lands near 7 GiB, leaving room for the host's desktop. Raise `--n-gpu-layers` in steps of two while `nvidia-smi` **on the inference host** still reports free memory, up to roughly sixteen - noting each four layers added pulls another twelfth of the cache onto the card too; spilling into shared memory costs far more than the layers gained. Generation is bound by that host's DDR5 bandwidth at roughly 2 GB of active weights per token - measure prompt processing and generation separately rather than trusting a quoted figure.
- **Dev host (where code is built and the app is seen):** measured RTX 3070 Ti with 8 GB VRAM, 128 GB DDR4-3600, 16 cores / 32 threads. Nothing about the model depends on this box, so do not size the model against it. What it does decide: compiles and tests run here, and the viewport measures only **~75 MB of VRAM**, so building and visually testing PolyCraft never competes with the model, which lives on the other host. Running the model here instead would be DDR4-bound at ~46 GB/s effective, on the order of 20-28 tok/s.
- **Context budget: 131,072 tokens - the right setting for this project, so leave it.** A larger ceiling is nearly free once prefix reuse works: what costs time is *re-prefilling*, not reserving slots, and this model's GQA cache is only 96 KiB per context token, so 128k puts about **1.6 GiB** in VRAM at the split above (12 GiB at full FP16, x 12/48 layers on GPU, x 0.53 for `q8_0`). Going to 256k would need 3.2 GiB and buys nothing this repo can spend - no task here reads more than a few files - while long-range attention quality degrades for a 30B model and the harness starts carrying stale tool output that dilutes the prompt. Going lower forces the digest or the working set out. Keep this digest **byte-identical and at the same position** in every prompt so the prefix KV cache is reused; re-prefilling it each turn is the dominant cost. **The ceiling is 12k tokens, and `scripts/check_digest.ps1` enforces it** - prose limits get forgotten, so run the script as part of every §8 handoff and treat its warning as a failing test. It is currently ~10.6k (~39k characters), roughly 8% of the window. Grow by **replacing, not appending**: when a change lands, delete or compress what it obsoletes before adding a new sentence, and never let two sections state the same rule - §7 is where that drifts first, because feature prose wants to re-explain mechanics that §3.5 and §5 already own; state a rule once there and let §7 point at it. `--keep` must stay above the digest's token count or its head begins evicting and every turn re-prefills what it lost, which is why it is set to the **ceiling** rather than today's figure - do not lower it to match the current size. The server's `--ctx-size` must be at least what the harness is set to, or requests are truncated silently.
- **Flag spellings drift between llama.cpp builds** (recent builds want `--flash-attn on`), so confirm each one with `llama-server --help` on the inference host before treating the line above as runnable. Serving to the dev host needs `--host`/`--port` and a firewall rule; LAN round-trip latency is negligible beside prefill, so it is not worth optimising.
- **Do not** feed the whole repo to the model. Use the §4 map to name the exact file(s) to read, then supply only those.

## 1. Project Vision
PolyCraft is a trimmed-down Maya clone written in Rust, built to leverage decades of learned muscle memory (e.g., V-key vertex snapping, D-key pivot editing, Q/W/E/R tool switching).
- **Core Features:** Polygon modeling, FBX export, pie menus, manipulator gizmos.
- **Explicit Non-Goals:** Advanced rendering (mental ray/Vray), physics, fluids, particles, NURBS, Output Window, complex construction history beyond immediate operations.

## 2. Tech Stack & Dependencies
- **Language:** Rust 2021 edition (Windows / MSVC ABI). Toolchain in use is rustc 1.95.x; there is **no `rust-version` key in `Cargo.toml`** and no `rust-toolchain.toml`, so the floor is only implied (the `Cargo.lock` is spec `version = 4`, which needs Cargo 1.85+). Do not assume 1.80 will build it.
- **Graphics:** `wgpu` 0.20 (lockfile 0.20.1, DirectX 12 backend), `winit` 0.29 (0.29.15), `pollster` 0.3, `bytemuck` 1.25, `cgmath` 0.18. `naga` sits at 0.20.0 through `wgpu`.
- **UI:** `egui` / `egui-wgpu` / `egui-winit` 0.28 (0.28.1, immediate mode for pie menus and tool hints).
- **Geometry:** A custom half-edge mesh stored as three plain `Vec`s (`vertices`, `half_edges`, `faces`) addressed by `usize` newtypes (`VertexId`, `HalfEdgeId`, `FaceId`). There is **no `Arena`, `slotmap`, or `index_vec`** anywhere in the dependency tree - do not go looking for one. The `HashMap`/`HashSet` in `mesh.rs` are for `EdgeId` grouping only, not for storage.
- **Dependency Coupling:** Versions in `Cargo.toml` are tightly coupled (e.g. `egui` 0.28 pairs strictly with `wgpu` 0.20). Upgrading one usually requires upgrading all. Do not add external crates without checking if the existing stack already covers the requirement.

## 3. Architectural Rules
- **Context Management:** Code is modularized. Keep files focused; prefer creating a new module over letting `main.rs` grow excessively.
- **State Management:** Strict decoupling. `State` (in `renderer.rs`, not `main.rs`) encapsulates all `wgpu` initialization, render pipeline dispatch, and viewport interaction state. The `winit` event loop in `main.rs` strictly routes OS events and touches `State` only through its public surface - `window`, `size`, `on_window_event`, `wants_keyboard_input`, `handle_cursor_moved`, `handle_mouse_input`, `handle_hotkey`, `process_mouse_motion`, `process_scroll`, `set_alt_pressed`, `set_shift_pressed`, `set_ctrl_pressed`, `resize`, `render` - and never a field directly. Multi-field operations go through those interaction seams rather than pairs of accessors because a seam can split-borrow `self.camera_controller` and `self.camera` while two separate accessors each borrow all of `state` and fail to compile (E0499). `undo`/`redo`/`cancel_active_drag` are also `State` methods for the same reason.
- **Scene Ownership:** `scene.rs` owns the editable document: the mesh, the `EditMode`, `Selection`, active `Tool`, and the undo/redo `HistoryStack`. Change them only through the `Scene` API (`set_mode()`, `set_tool()`, `select_at()`, `translate_vertices()`, the extrude drag quartet `begin_extrude_drag`/`preview_extrude`/`commit_extrude`/`abandon_extrude`, `begin_action()`/`end_action()`/`cancel_action()`, `undo()`/`redo()`). Mesh access is **read-only by design** - `mesh()` hands out `&HalfEdgeMesh` and there is deliberately no mutable handle, so a geometry change has to be an operation with validation and a history step rather than a field write the undo stack never saw. Document mutations flag `dirty = true`; `State::render` calls `take_dirty()` to rebuild GPU buffers.
- **UI Returns Intent:** `ui.rs` never mutates application state directly. `UiState::draw` takes what to display as a `UiContext` struct (`mode`, `tool`, `selected_count`, `can_undo`, `can_redo`, `undo_label`, `redo_label`, `can_extrude`, `extruding`, `notice`, `space`) and returns what the user asked for (`UiResponse { mode, tool, undo, redo, extrude, space }`); `renderer.rs::apply_ui_response` is the single place that applies it, so a button, a pie flick and a hotkey cannot drift apart. The two halves differ deliberately: `UiResponse` derives `Default`, so a new intent costs one field and one `response.x = true` and no call sites, while `UiContext` is a plain struct built at **four** places - the production one in `renderer.rs` plus `test_context()`, `undoable_context()` and `redoable_context()` in `ui.rs` - so a new display field is four edits, and leaving one out is a compile error rather than a silently greyed-out control.
- **Hotkeys Stay a Pure Map:** the Maya keymap lives in `renderer.rs::hotkey_for(key, ctrl, shift) -> Option<Hotkey>`, a free function that `State::handle_hotkey` carries out. Binding a key is adding a match arm; asserting one is a unit test - no window, no GPU context. `main.rs` only decides *whether* to offer the key (skipping it when the UI consumed the event or owns keyboard focus).
- **Pure Logic Stays Testable:** Mesh topology, topology edits, picking, selection, camera math, gizmo calculations, and the `HistoryStack` never touch `wgpu` or `winit`, and have unit tests next to the code (`mod tests`). `HistoryStack<T>` is generic over the snapshot type, so stack semantics are tested with `T = i32`.
- **Render Passes:** 3D Scene renders first with Z-buffer depth. `egui` renders second with `LoadOp::Load` to draw on top.
- **Resilient Error Handling:** Recoverable errors must be handled gracefully rather than panicked; the application must not crash on surface resizes, minimize events, or transient GPU adapter conditions. (Known gap: `State::new` and `main.rs` still `unwrap()` surface/adapter/shader setup and `gizmo::pivot` at drag start - 5 in `renderer.rs` outside `mod tests`, 2 in `main.rs`. Prefer `.expect("what failed and why")` in new code.)

### 3.5 Failure Modes
The gotchas that carry no compile error. The rules they protect are in §3 and §5; only the symptom is listed here.
- **Hand-building shaded vertices** instead of calling `HalfEdgeMesh::generate_render_buffers()` desynchronizes un-welded vertices from `vertex_faces`, so shading and wireframe disagree with the geometry.
- **Narrowing `RenderMesh::indices` from `u32` to `u16`** wraps silently onto the wrong vertices rather than failing, because vertices are un-welded per face and a modest model passes 65,536 of them. The pass binds `IndexFormat::Uint32`.
- **A mutation left out of `begin_action`/`end_action`** still renders correctly but never reaches history, so `Ctrl+Z` skips straight past that operation.
- **A `GpuVertex`/`CameraUniform` change made in only one place** (struct, layout/bind group, or `shader.wgsl` `@location`) yields a garbled or blank viewport with no compile error.
- **The gizmo is translate-only.** `upload_gizmo()` and `handle_mouse_input()` gate on `Tool::Translate`; removing that gate lets a drag start on an axis that was never drawn. Rotate and Scale are labels today.
- **A mislinked half-edge has no symptom.** It compiles, renders almost correctly, and only then panics inside the `expect` in `half_edge_destination`/`face_half_edges` - or silently returns another face's corners. `mesh_edit.rs` primitives cannot leave you with this (they validate the candidate before installing it), but an edit hand-wired outside them can - see §5.
- **Reusing an `EdgeId` across the edit that moved it.** Ids stay valid, so nothing errors - the selection just quietly stops matching what the user pointed at. After a `split_edge`, or a whole ring of them across an `insert_edge_loop`, the id names a vertex pair that no longer exists and the edge becomes unselectable; take the replacements from the returned `SplitEdge`/`EdgeLoopCut`. After a `bevel_edge` it is worse, because both endpoints are *reused* as corners of the new facet: the same pair still resolves, to the facet's near edge a bevel's width from where the original ran, so a stale highlight or a second bevel answers with geometry nobody selected. The rule for every operation is the same - **rebuild the selection from the ids the edit returns**, never from the ids it consumed; bevel returns `corners` and `Scene` re-derives the facet's outline from them.

### 3.6 Test Placement
Tests live in each file's bottom `mod tests`, and pure-module tests never open a window or a GPU context. Put new *logic* in a pure module and test it there. Put new *wiring* in `renderer.rs` and test it the way `hotkey_for` and `drag_action_label` already are: as a free pure function the seam calls, asserted directly.

## 5. Conventions & Invariants
- **Coordinate Space:** Right-handed, Y-up. Front faces wind counter-clockwise (`FrontFace::Ccw`, back-face culling on).
- **Flat Shading:** One normal per face (Newell's method in `face_normal`). Render vertices are un-welded, and `RenderMesh::vertex_faces` records which face each one came from. Faces are triangulated as fans (must remain convex).
- **Component IDs:** `VertexId`, `HalfEdgeId`, `FaceId` are `usize` newtypes indexing the `Vec`s in `HalfEdgeMesh`. `EdgeId` is an undirected pair of vertex indices (smaller first), so both half-edges of an edge produce the identical id.
- **Append-Only Storage:** the three `Vec`s grow and never shrink, which is what makes a bare `usize` a stable reference and what lets `Scene::restore` clip a restored selection by range alone (`v.0 < vertex_count`). Extrude, bevel and cut must preserve that: move and rewire in place, append new components, never `swap_remove` or truncate. Removal is a different problem - compacting a `Vec` leaves an in-range id naming a *different* component, so `delete` needs tombstones or generational ids plus an identity-based selection check.
- **Validate After Every Edit:** `HalfEdgeMesh::validate() -> Result<(), TopologyErrors>` reports every violated invariant in one pass - dangling id, asymmetric twin, `next`/`prev` disagreement, open or shared face loop, orphan vertex, non-manifold directed edge, **duplicate face** (two faces over the same corner set), **zero-area face**, **disconnected vertex fan** (a pinch). `mesh_edit.rs` makes this structural rather than advisory: each primitive refuses a bad argument, rewires a **clone**, `validate()`s the clone, and installs it only if it holds - so a refused edit leaves the document byte-identical and nothing has to be undone. Checking the *candidate* rather than the input is also what blocks editing a mesh that already arrived broken. Three production paths reach it, all through `Scene`: `extrude_faces` via `begin_extrude_drag` then `preview_extrude` on each cursor move and `commit_extrude` or `abandon_extrude` to close it, `insert_edge_loop` on Shift+L, and `bevel_edge` on Shift+B.
- **Edit primitives are all-or-nothing and total:** every fallible read on the edit path is `Option`-safe (`destination_of`, `edge_id_of`) instead of the `expect`-based queries in `mesh.rs`, because an edit is how bad topology gets *reported* and must describe damage rather than panic on it. `add_vertex` may leave a vertex unclaimed mid-sequence - legal, since nothing validates until the candidate is checked, and how `append_face` builds a mesh from nothing.
- **Edits invalidate the `EdgeId` they consumed** - see §3.5 for why that is silent and what to do. Component ids themselves stay stable (append-only). `SplitEdge` returns the replacement `vertex`, `edges` and `half_edge`; `EdgeLoopCut` and `Beveled` return the ids each operation created.
- **Half-edge record shape:** `HalfEdge { origin, twin, next, prev, face }` - the opposite half-edge is `twin`, not `opposite`, and `twin`, `next`, `prev` and `face` are all `Option` (a boundary edge has no twin). `MeshVertex { position, half_edge }` stores one outgoing half-edge, also `Option`. There is no destination field; use `half_edge_destination()`.
- **Screen-Space Tolerances:** Picking and gizmo arm tolerances are measured in screen pixels (`VERTEX_PICK_RADIUS_PIXELS`, `EDGE_PICK_RADIUS_PIXELS`, `GIZMO_PICK_TOLERANCE_PIXELS`) via `world_per_pixel()`, maintaining consistent feel at any zoom level. Components behind nearer faces are occluded; gizmo arms bypass depth occlusion (`Always` pass).
- **Selection Semantics:** One selection set per component kind; switching `EditMode` drops other kinds. Plain click replaces selection, Shift+click toggles, and plain click on empty space clears (Maya semantics).
- **Tool Independence:** Active tool (`Tool::Select`, `Tool::Translate`, `Tool::Rotate`, `Tool::Scale`) is decoupled from `EditMode`. Switching modes preserves tool; switching tools preserves selection.
- **GPU Vertex Layout Sync:** `GpuVertex` (and `CameraUniform`) live in `src/render_types.rs` and derive `bytemuck::Pod`/`Zeroable`. One struct serves every pass - `position` plus `normal`, which carries a surface normal for shaded faces but a screen-pixel offset for billboarded vertex dots - so it must stay strictly in sync with the single `wgpu::VertexBufferLayout` and the `@location(n)` declarations in `shader.wgsl`. `overlay.rs` exposes it as `OverlayVertex` via a type alias; do not reintroduce a second vertex struct.

## 7. Status (update at the end of every task)
Write what the app *does now*, not how it got here. The per-iteration narrative lives in `git log`; do not re-grow a build history here - it is the first thing to go stale and the last thing a model needs.
- **Working (run-tested):**
  - Flat-shaded cube from the half-edge mesh with Newell normals.
  - Maya camera navigation: Alt+LMB orbit, Alt+MMB pan (consistent screen-space tracking), Alt+RMB / scroll zoom.
  - Marking pie menu: hold RMB (without Alt) or Spacebar, flick toward a slot and release to switch `EditMode` (Edge=Up, Face=Down, Vertex=Left, Object=Right).
  - Viewport click-to-select: plain LMB click casts NDC ray; Shift+click toggles selection; empty click clears.
  - Visual overlays: selected faces tinted Maya warm orange, selected object tinted Maya green; wireframe edges with depth bias (cyan for selected); vertex square dots in Vertex mode (blue for unselected, bright yellow for selected).
  - Tool system: Q (Select), W (Move), E (Rotate), R (Scale) hotkeys and "PolyCraft Tools" egui panel.
  - Transform Gizmo (`W` Move tool): constant-pixel-size 3D axes drawn with `Always` depth at the selection pivot. Hovering an axis highlights it bright Maya yellow; dragging one translates the selected components live, normals and wireframe recalculated as they go; releasing commits and Escape restores the positions taken at grab.
  - Reference System (`X`, or the "Gizmo:" row): Maya's reference-system control, choosing whether the handle is drawn and dragged in `Space::World` or `Space::Component`. Component takes its orientation from the selected geometry - a face's normal, **an edge's averaged adjacent-face normal** (not the edge's own direction: pulling Z should lift the edge out *between* the faces meeting at it, as Maya does, not slide it along itself; the edge line still carries X), or a vertex's averaged surrounding faces - so a move out of a tilted face is draggable without hunting for the nearest world axis. It falls back to World when the selection has no single direction (nothing selected, opposite faces cancelling, Object mode) rather than drawing nothing. There is deliberately **no `Space::Object`**: the document is one mesh with vertices in world coordinates and no transform anywhere, so an object frame would be numerically identical to World while implying a hierarchy the app lacks - add the variant when an object transform lands, not before. `DragState` stores the `Frame` it was grabbed with, so switching space mid-drag cannot lurch geometry already in flight, and draw, hover-pick and drag all read that one frame - which is why `renderer.rs` no longer hardcodes `axis.unit_vector()` in its arm geometry. Cycling space never abandons an armed extrude (extrude travels the faces' own normals, which no space changes) and never marks the document dirty, since no vertex moved.
  - Undo / Redo: `Ctrl+Z` steps back, `Ctrl+Y` and `Ctrl+Shift+Z` step forward. A whole gizmo drag is a single step; a press-and-release that moved nothing records no step, so `Ctrl+Z` after a stray click lands on the previous real action. Undo restores geometry and selection but never the `EditMode` or `Tool`. The Undo / Redo buttons in the "PolyCraft Tools" panel name the action each would perform and grey out when the history runs out.
  - Extrude: `Shift+E` **arms a drag**; the mouse sets how far the faces travel, click settles the depth, Escape abandons and restores. The handle is drawn in the selected faces' own frame - `gizmo::Frame::from_axis(pivot, normal)`, which is what Maya calls component space - and depth is read along it, so the axis the user grabs is the axis the geometry moves. Faces travel along **the average of their own normals, recomputed from the live mesh on every arm**, and a wall grows behind each edge of the selection nothing else bounds. Averaging sends a two-face corner out diagonally as Maya does; normals that cancel (two opposite faces) are refused rather than pushed by a zero vector. **No direction is ever remembered** - an earlier build cached one and reused it for any selection inside it, which made a picked wall slide sideways through the prism. The faces that moved stay selected rather than the walls, so pressing again grows the same lump and a wall the user then picks travels along *its* normal. Refusals reach the panel's command echo with their reason - nothing selected, no common direction, or a corner that would be stranded. `UiContext.extruding` keeps panel and viewport telling the same story (button reads "Extrude" greyed / "Extrude  (Shift+E)" live / "Click to set depth" mid-gesture) and `State::commit_extrude_drag` runs before a click can be read as a selection. Orbiting mid-gesture must not bank as depth: `CameraController::is_navigating()` gates cursor tracking, `DragAnchor::mark_swung` re-baselines the projection because a projection measured from a new sight line is a different number, and `DragAnchor::advance` clamps each step to `MAX_EXTRUDE_STEP_ARMS` arm-lengths so a flick cannot fling geometry.
  - Insert Edge Loop (`Shift+L`, or the panel button): Maya's *Insert Edge Loop Tool*, run through the **one** edge selected in Edge mode. `mesh_edit::edge_loop_crossings` walks the ring - enter a quad, exit by the edge opposite, cross the `twin`, repeat - and for each face crossed the ring edge is opened with `split_edge` at its midpoint, then the face is cut between its two new corners with `split_face`. Composition is the design: every step validates its own result, so the ring either lands whole or nothing does, and no new primitive-level invariant had to be invented. Quads only, and **the ring stops where the quads stop**: "the edge opposite this one" is not a thing an n-gon has - nearest corner and halfway round give different answers as soon as there are five corners - so the walk ends at a five-cornered face rather than guessing, exactly as it ends at an open boundary, and the cut is laid down as far as it can be measured so **where it stopped is visible in the mesh**. Refusing the whole ring instead would let one n-gon anywhere turn the tool dead, so only a ring that cannot even *start* (a seed edge bounding no face) is refused - cutting nothing is indistinguishable from a dead key. A ring that runs off an open boundary is likewise cut as far as it goes. The new ring is left selected, so pressing again cuts from the ring under the cursor; two edges selected is refused with a reason (they can name the same ring, and the second would arrive to find its edges already split). The edges the ring passed through are dead ids afterwards - see §3.5 - so take ids from the returned `EdgeLoopCut`. One history step, labelled "Insert Edge Loop"; a refusal lands none.
  - Bevel (`Shift+B`, or the panel button): Maya's *Bevel*, on the **one** edge selected in Edge mode. `mesh_edit::bevel_edge(edge, amount)` slides the two faces that bounded the edge apart and fills the gap with a flat facet, so a cube edge takes the solid from 8 vertices / 12 edges / 6 faces to **10 / 15 / 7** and leaves the two faces that met the edge at its endpoints as pentagons. `amount` (Scene's `BEVEL_AMOUNT`) is a **fraction of each adjoining edge, not a distance**, so one setting reads the same on a unit cube and on a hundred-unit terrain; past about a third the facet starts eating the faces either side instead of standing between them. **No deletion was needed** - the facet is appended, the two bounding faces keep their corner counts, and only the endpoints relocate - so the tombstone work in §5 is still not on the critical path, and this file's earlier prediction that bevel would require it was wrong. Two refusals, each naming its reason: a boundary edge (a rim around an opening is a different construction), and a corner where more than two other faces also meet, which is any corner of degree four or higher - Maya splits those once per diverging face, and here they would strand vertices. **Selection goes to the facet's four edges, deliberately breaking extrude's keep-what-you-picked rule**, because the `EdgeId` handed in resolves to the wrong edge afterwards - the case spelled out in §3.5. `BevelCommit { facet, facet_edges }` is the record of what moved. One history step, "Bevel Edge"; a refusal lands none and touches nothing.

Covered alongside the pure picking math is `picking::Ray::from_screen` (top-left pixel origin to NDC ray, used by `State::cursor_ray`). The gizmo math is pure and tested: `GizmoAxis`, `pivot()`, `axis_world_length()`, `arms()`/`translate_arms()` (active yellow `COLOR_AXIS_ACTIVE`), `pick_frame_axis()` via `picking::ray_segment`, `project_ray_onto_axis()`, `selected_vertices()`, `Space` and `selection_axis()`, and `Frame` (`world`/`from_axis`/`direction`/`arm_end`) - including that `from_axis` yields a right-handed frame whose first axis is the geometry's own normal and refuses an axis with no direction, that a frame's arms reach along its own directions rather than the world's, and that picking follows the frame. `renderer.rs` seams are tested through the free functions they call - `hotkey_for(key, ctrl, shift) -> Option<Hotkey>`, `drag_action_label(mode, tool)` (yields "Move Vertex" / "Move Edge" / "Move Face" / "Move") and `DragAnchor` (`advance`/`mark_swung`) - asserted directly with no window. The panel is tested frame-level by driving `UiState::draw` through egui with synthetic input, which is also how the pie menu's slot and tie behaviour is pinned (`slot_toward`).

  - Topology safety net: `HalfEdgeMesh::validate()` walks every invariant in §5 in one linear pass and returns them all as `TopologyErrors` rather than the first one. Its tests break the cube deliberately - one per invariant - and assert the failure is *named*, not merely present. Three matter most: a lone quad validates (boundary edges are legal, which extrude depends on), two faces sharing a directed edge do not (the non-manifold case `from_faces` accepts by overwriting its own twin lookup), and two faces over the same corners running the ring *backwards* do not either - they share no directed edge and every twin links up, so only `check_faces_are_distinct` sees the overlap. Ids are resolved into plain `Option<usize>` before any pass, so a mesh naming a nonexistent component is described instead of panicking inside a query while being diagnosed. The three geometric passes (`check_faces_bound_area`, `check_faces_are_distinct`, `check_vertex_fans_are_connected`) share one `walk_face` helper that steps over an unwalkable face rather than raising a second, vaguer complaint about damage already on the list.
  - Edit primitive layer, `src/mesh_edit.rs`: read side `boundary_edges()`, `is_boundary_edge()`, `outgoing_half_edges()`, `vertex_is_boundary()`; write side `add_vertex()`, `append_face(&[VertexId])`, `split_edge(EdgeId, Point3)`, `split_face(FaceId, VertexId, VertexId)`, `insert_edge_loop(EdgeId) -> Result<EdgeLoopCut, _>`, `extrude_faces(&[FaceId], Vector3) -> Result<Extruded, _>` with its single-face wrapper `extrude_face`, and `bevel_edge(EdgeId, f32) -> Result<Beveled, _>`. Tests assert the hull both ways (closed cube empty, lone quad all four edges, two joined quads losing only the shared edge), that `append_face` caps an open box into a closed solid and twins the rim, that `split_edge` grows exactly the two faces bordering the edge and leaves the other four alone, and that every refusal leaves the mesh `PartialEq`-identical. Two matter most: **a cube built one face at a time from `HalfEdgeMesh::new()` with only `add_vertex` + `append_face` matches `create_cube()`** (proof the layer can author geometry), and **extruding a cube face leaves the solid closed** - every half-edge twinned, `boundary_edges()` empty, 60 indices from 10 quad faces - because a wall that merely parked its own half-edges instead of linking twins would still render and only show up here.
- **Not built yet:** Rotate and Scale are labels only - the gizmo and drag path implement `Tool::Translate` alone. Remaining edit operations are delete / cut and per-face (`inflate`) extrude; then FBX export.
  - **The write layer is live.** `extrude_faces` is its first production caller, so both `#![allow(dead_code)]` attributes that headed `mesh_edit.rs` and `Scene::mesh_mut()` are gone - keep it that way, since a reappearing one means new write code with no caller. `mesh.rs` itself keeps only record types, read-only queries and `validate()`; new *write* code belongs in `mesh_edit.rs` (an extension `impl HalfEdgeMesh`) so the panic-free edit path stays in one file.
  - **Gaps a cut or delete will hit:** nothing removes or flips anything, so every operation so far builds by appending and re-pointing - extrude never deletes its source face and bevel never removes a corner, only relocates one. **Delete is therefore the first operation that needs real removal**, and so the first that needs the tombstone / generational-id work in §5; that debt is what kept extrude, loop cut and bevel simple, and none of them paid it. Still not validated after the geometric passes: a miswound *boundary* face (undetectable without geometry - only twinned-edge winding conflicts are caught), faces that cross each other in space without sharing corners, since `MIN_FACE_AREA` judges area not intersection, and **a vertex joined by a single edge** - `check_vertices` only asks that a vertex start *some* edge and `check_vertex_fans_are_connected` only complains above one fan, so a degree-one spike passes both. It is unreachable while every operation appends, since only a delete can strand one, so the check belongs with delete rather than as code no path can fire. `MIN_FACE_AREA` is absolute rather than scale-relative, so a model imported at a thousandth of a unit would have its faces judged against a human-scale floor.
- **Known limitations:** fan triangulation assumes convex faces; the graphics backend is whatever `Instance::default()` picks (D3D12 on this machine, not pinned in code); the single `dirty` flag re-uploads mesh *and* overlay buffers together, so split them before driving very high-frequency drags; `HISTORY_DEPTH` (64) bounds undo by snapshot memory, which is a few hundred KB per step at current model sizes. `cargo check`, `cargo test` (241 passing), `cargo clippy --all-targets` and `cargo clippy --all-targets --all-features -- -D warnings` (all 0 warnings) pass as of this update, and the app launches to a stable viewport with empty stderr.
- **Next Milestone - removal, then Rotate/Scale:** extrude, loop cut and bevel have each proven the same shape, so keep it: one `Scene` method returning the new topology, refusing with reasons and changing nothing when it refuses, then a `renderer.rs` seam that abandons any drag, calls it, and echoes the outcome; one history step per gesture. The order matters. **`delete` is the milestone that changes the storage model**, because it is the first operation that must *remove* components rather than append and re-point - so it needs tombstones or generational ids first (see Append-Only Storage above), and any cut inherits that decision. Rotate and Scale are the cheaper visible win and need no topology work at all: the gizmo already draws three arms and `DragState` records the axis grabbed, so what is missing is applying a rotation or scale to `selected_vertices()` instead of a translation, which means a pivot and an angle-to-matrix conversion rather than new mesh invariants. Extrude's remaining open edge is that a divergent selection is pushed along one shared direction rather than per face, so Maya's inflate is not available yet; per-face depth would also want the drag to carry more than one axis.
  - Build each operation as `Scene` methods that return what changed, opening one history step when the gesture starts and closing it when it settles, so it lands as a single undoable action. Extrude shows what that takes: the opening call snapshots the mesh *and* calls `begin_action`; each preview rebuilds **from the snapshot** rather than the live mesh, so a drag is a position not a delta - back the cursor up and the faces come back; commit closes with `end_action`, abandon reinstates the snapshot and calls `cancel_action`. Any `end_action` without a matching change records nothing, so a stray keypress cannot pollute the undo chain.
  - **Selection after an edit is a decision each operation must make, not a detail.** Extrude's precedent: **keep the components the user pointed at** - append-only storage lets a moved face retain its id, so nothing needs rewriting and repeat-press accumulates. **A deliberate divergence from Maya**, which hands selection to the newly created walls; do not "correct" it back. An operation that *replaces* components has no surviving id to hold and must state its own hand-off rather than copying this - bevel does, above. `Scene::restore` bounds-checks a restored selection against live ids.
  - Index generation no longer caps model size: `RenderMesh::indices` is `Vec<u32>` and the render pass binds `IndexFormat::Uint32`, so extrusion can push past 65,536 un-welded vertices.
  - Followed by FBX export.
