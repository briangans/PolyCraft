# PolyCraft - AI Context Digest

## 0. Model & Harness Configuration
Two machines are involved and **their limits must not be transferred between them**. The *inference host* runs the model and the harness; the *dev host* runs VS Code, the agent extension, and PolyCraft itself. This file is written to be pasted whole into one prompt.
- **Inference host (runs the model):** 12 GB VRAM, 96 GB DDR5. Model: Qwen3-Coder-30B-A3B-Instruct, `Q4_K_M` - 30.5B parameters, 3.3B active per token, 48 layers, 262,144 native context. The 18.56 GB file exceeds 12 GB of VRAM, so layers split across GPU and system RAM: `--n-gpu-layers 12 --flash-attn --ctx-size 65536 --parallel 1 --cache-type-k q8_0 --cache-type-v q8_0 --jinja --mlock --threads <physical cores> --keep 12000 --cache-reuse 256`.
- **Sizing math:** grouped-query attention gives 4 KV heads at `head_dim` 128 over 48 layers, so the KV cache is 2 x 4 x 128 x 48 x 2 bytes = **96 KiB per context token** in FP16, 51 KiB at `q8_0` - 6.0 GiB at 128k, 3.2 GiB at 65k. **The cache follows the layer split**, so at `--n-gpu-layers 12` only 12/48 of it is in VRAM: about 1.5 GiB at 128k, the rest in system RAM. Each layer is 17.28 GiB / 48 = **0.36 GiB**, so twelve layers (4.3 GiB) plus 1.5 GiB of KV plus roughly 1.2 GiB of compute buffers lands near 7 GiB, leaving room for the host's desktop. Raise `--n-gpu-layers` in steps of two while `nvidia-smi` **on the inference host** still reports free memory, up to roughly sixteen - noting each four layers added pulls another twelfth of the cache onto the card too; spilling into shared memory costs far more than the layers gained. Generation is bound by that host's DDR5 bandwidth at roughly 2 GB of active weights per token - measure prompt processing and generation separately rather than trusting a quoted figure.
- **Dev host (where code is built and the app is seen):** measured RTX 3070 Ti with 8 GB VRAM, 128 GB DDR4-3600, 16 cores / 32 threads. Nothing about the model depends on this box, so do not size the model against it. What it does decide: compiles and tests run here, and the viewport measures only **~75 MB of VRAM**, so building and visually testing PolyCraft never competes with the model, which lives on the other host. Running the model here instead would be DDR4-bound at ~46 GB/s effective, on the order of 20-28 tok/s.
- **Context budget: 65,536 tokens - what Strata on the inference host is configured to. Treat it as the constraint, not a choice.** The server's `--ctx-size` must be **at least** the harness setting or requests are truncated silently, so run it at 65536 and leave both equal; going higher costs little (see the sizing math above) but buys nothing this repo can spend - no task reads more than a few files - while long-range attention quality degrades for a 30B model and the harness starts carrying stale tool output that dilutes the prompt. Keep this digest **byte-identical and at the same position** in every prompt so the prefix KV cache is reused; re-prefilling it each turn is the dominant cost, and `--keep` must stay above its token count - which is why it is set to the **ceiling**, not to today's figure; do not lower it to match. **The ceiling is 12k tokens; `scripts/check_digest.ps1` prints the current figure and enforces it** - prose limits get forgotten, so run the script at every §8 handoff and treat its warning as a failing test. The figure is deliberately *not* restated here: any number written into this file is wrong the moment the file grows, which is exactly the drift the script exists to catch. Grow **by replacing, not appending**: when a change lands, compress or delete what it obsoletes before adding a sentence, and never let two sections state the same rule - §7 is where that drifts first, because feature prose wants to re-explain mechanics that §3.5, §5 and the source doc comments already own.
- **Flag spellings drift between llama.cpp builds** (recent builds want `--flash-attn on`), so confirm each one with `llama-server --help` on the inference host before treating the line above as runnable. Serving to the dev host needs `--host`/`--port` and a firewall rule; LAN round-trip latency is negligible beside prefill, so it is not worth optimising.
- **Do not** feed the whole repo to the model. Use the §4 map to name the exact file(s) to read, then supply only those.

## 1. Project Vision
PolyCraft is a trimmed-down Maya clone written in Rust, built to leverage decades of learned muscle memory (e.g., V-key vertex snapping, D-key pivot editing, Q/W/E/R tool switching).
- **Core Features:** Polygon modeling, FBX export, pie menus, manipulator gizmos.
- **Explicit Non-Goals:** Advanced rendering (mental ray/Vray), physics, fluids, particles, NURBS, Output Window, complex construction history beyond immediate operations.

## 2. Tech Stack & Dependencies
- **Language:** Rust 2021 edition (Windows / MSVC ABI). Toolchain in use is rustc 1.95.x; there is **no `rust-version` key in `Cargo.toml`** and no `rust-toolchain.toml`, so the floor is only implied (the `Cargo.lock` is spec `version = 4`, which needs Cargo 1.85+). Do not assume 1.80 will build it.
- **Graphics:** `wgpu` 0.20 (lockfile 0.20.1, DirectX 12 backend), `winit` 0.29 (0.29.15), `pollster` 0.3, `bytemuck` 1.25, `cgmath` 0.18. `naga` sits at 0.20.0 through `wgpu`.
- **UI:** `egui` / `egui-wgpu` / `egui-winit` 0.28 (0.28.1, immediate mode for pie menus and tool hints).
- **Geometry:** A custom half-edge mesh stored as three plain `Vec`s (`vertices`, `half_edges`, `faces`) addressed by `usize` newtypes (`VertexId`, `HalfEdgeId`, `FaceId`). There is **no `Arena`, `slotmap`, or `index_vec`** anywhere in the dependency tree - do not go looking for one. The `HashMap`/`HashSet` in `mesh.rs` are for `EdgeId` grouping only, not for storage.
- **Dependency Coupling:** Versions in `Cargo.toml` are tightly coupled (e.g. `egui` 0.28 pairs strictly with `wgpu` 0.20). Upgrading one usually requires upgrading all. Do not add external crates without checking if the existing stack already covers the requirement.

## 3. Architectural Rules
- **Context Management:** Code is modularized. Keep files focused; prefer creating a new module over letting `main.rs` grow excessively.
- **State Management:** Strict decoupling. `State` (in `renderer.rs`, not `main.rs`) encapsulates all `wgpu` initialization, render pipeline dispatch, and viewport interaction state. The `winit` event loop in `main.rs` strictly routes OS events and touches `State` only through its public surface - `window`, `size`, `on_window_event`, `wants_keyboard_input`, `handle_cursor_moved`, `handle_mouse_input`, `handle_hotkey`, `process_mouse_motion`, `process_scroll`, `set_alt_pressed`, `set_shift_pressed`, `set_ctrl_pressed`, `resize`, `render` - and never a field directly. Multi-field operations go through those interaction seams rather than pairs of accessors because a seam can split-borrow `self.camera_controller` and `self.camera` while two separate accessors each borrow all of `state` and fail to compile (E0499). `undo`/`redo`/`cancel_active_drag` are also `State` methods for the same reason.
- **Scene Ownership:** `scene.rs` owns the editable document: the mesh, the `EditMode`, `Selection`, active `Tool`, and the undo/redo `HistoryStack`. Change them only through the `Scene` API (`set_mode()`, `set_tool()`, `select_at()`, `translate_vertices()`, the extrude drag quartet `begin_extrude_drag`/`preview_extrude`/`commit_extrude`/`abandon_extrude`, `begin_action()`/`end_action()`/`cancel_action()`, `undo()`/`redo()`). Mesh access is **read-only by design** - `mesh()` hands out `&HalfEdgeMesh` and there is deliberately no mutable handle, so a geometry change has to be an operation with validation and a history step rather than a field write the undo stack never saw. Document mutations flag `dirty = true`; `State::render` calls `take_dirty()` to rebuild GPU buffers.
- **UI Returns Intent:** `ui.rs` never mutates application state directly. `UiState::draw` takes what to display as a `UiContext` struct (`mode`, `tool`, `selected_count`, `can_undo`, `can_redo`, `undo_label`, `redo_label`, `can_extrude`, `extruding`, `notice`, `space`) and returns what the user asked for (`UiResponse { mode, tool, undo, redo, extrude, space }`); `renderer.rs::apply_ui_response` is the single place that applies it, so a button, a pie flick and a hotkey cannot drift apart. The two halves differ deliberately: `UiResponse` derives `Default`, so a new intent costs one field and one `response.x = true` and no call sites, while `UiContext` is a plain struct built at **four** places - the production one in `renderer.rs` plus `test_context()`, `undoable_context()` and `redoable_context()` in `ui.rs` - so a new display field is four edits, and leaving one out is a compile error rather than a silently greyed-out control.
- **Every Pass Shares One Sample Count:** the viewport renders at `VIEWPORT_SAMPLE_COUNT` (4× MSAA) into a multisampled colour buffer with matching multisampled depth, resolving onto the surface as the pass closes because a surface texture cannot hold samples. Every pipeline, the resolve target and `resize` must name that same constant - a pipeline built with `sample_count: 1` against a 4× target fails device validation at first draw, not at compile time. It is what stopped the wireframe reading **dotted** at grazing angles: a 1px `LineList` landing on pixel centres irregularly dropped out for a column or two, so the same edge read solid from one angle and broken from another. Depth is sampled too, so silhouettes antialias rather than gaining jaggies.
- **Hotkeys Stay a Pure Map:** the Maya keymap lives in `renderer.rs::hotkey_for(key, ctrl, shift) -> Option<Hotkey>`, a free function that `State::handle_hotkey` carries out. Binding a key is adding a match arm; asserting one is a unit test - no window, no GPU context. `main.rs` only decides *whether* to offer the key (skipping it when the UI consumed the event or owns keyboard focus).
- **Pure Logic Stays Testable:** Mesh topology, topology edits, picking, selection, camera math, gizmo calculations, and the `HistoryStack` never touch `wgpu` or `winit`, and have unit tests next to the code (`mod tests`). `HistoryStack<T>` is generic over the snapshot type, so stack semantics are tested with `T = i32`.
- **Render Passes:** 3D Scene renders first with Z-buffer depth. `egui` renders second with `LoadOp::Load` to draw on top.
- **Resilient Error Handling:** Recoverable errors must be handled gracefully rather than panicked; the application must not crash on surface resizes, minimize events, or transient GPU adapter conditions. (Known gap: **6 `unwrap()`s, all at startup, none inside an event handler** - 4 in `State::new` (`create_surface`, `request_adapter`, `request_device`, `get_default_config`) and 2 in `main.rs` (`EventLoop::new`, `WindowBuilder::build`). So today a failure kills the process before a window ever appears rather than mid-session, which is why it is a gap and not a bug. `scene::extrude_pivot` is *not* part of this: it reads `gizmo::pivot` through `unwrap_or`, a documented fallback for a selection emptied underneath the drag. Prefer `.expect("what failed and why")` in new code.)

### 3.5 Failure Modes
The gotchas that carry no compile error. The rules they protect are in §3 and §5; only the symptom is listed here.
- **Hand-building shaded vertices** instead of calling `HalfEdgeMesh::generate_render_buffers()` desynchronizes un-welded vertices from `vertex_faces`, so shading and wireframe disagree with the geometry.
- **Narrowing `RenderMesh::indices` from `u32` to `u16`** wraps silently onto the wrong vertices rather than failing, because vertices are un-welded per face and a modest model passes 65,536 of them. The pass binds `IndexFormat::Uint32`.
- **A mutation left out of `begin_action`/`end_action`** still renders correctly but never reaches history, so `Ctrl+Z` skips straight past that operation.
- **A `GpuVertex`/`CameraUniform` change made in only one place** (struct, layout/bind group, or `shader.wgsl` `@location`) yields a garbled or blank viewport with no compile error.
- **A drawn arm and a live drag must agree about the tool.** `upload_gizmo` and `handle_mouse_input` both gate on `Tool::has_gizmo()`; changing one alone starts a drag on an arm that was never drawn. `DragState` also carries the `Tool` it was grabbed with - `E` arriving mid-pull must not reinterpret travel already banked as a turn of however far the mouse went.
- **A turn has no scalar, so it is accumulated in steps.** `SweepAnchor` stores the cursor's *bearing* across the ring's plane rather than its position: a rotate drag crosses the line of rotation routinely, and a position stored there has no bearing, which would freeze the turn from then on. The angle written is absolute (`rotate_vertices` rebuilds from the snapshot) but each step is clamped by `MAX_ROTATE_STEP_RADIANS`, because a near-edge-on view makes the projected bearing leap.
- **A mislinked half-edge has no symptom.** It compiles, renders almost correctly, and only then panics inside the `expect` in `half_edge_destination`/`face_half_edges` - or silently returns another face's corners. `mesh_edit.rs` primitives cannot leave you with this (they validate the candidate before installing it), but an edit hand-wired outside them can - see §5.
- **Reusing an `EdgeId` across the edit that moved it.** Ids stay valid, so nothing errors - the selection just quietly stops matching what the user pointed at. After a `split_edge`, or a whole ring of them across an `insert_edge_loop`, the id names a vertex pair that no longer exists and the edge becomes unselectable; take the replacements from the returned `SplitEdge`/`EdgeLoopCut`. After a `bevel_edge` it is worse, because both endpoints are *reused* as corners of the new facet: the same pair still resolves, to the facet's near edge a bevel's width from where the original ran, so a stale highlight or a second bevel answers with geometry nobody selected. The rule for every operation is the same - **rebuild the selection from the ids the edit returns**, never from the ids it consumed; bevel returns `corners` and `Scene` re-derives the facet's outline from them.
- **A `FaceId` or `VertexId` held across `delete_selected` names a different component.** Worse than the above: dense-packing shifts every id above a retired record *down*, so a stale selection highlights its neighbour - correct-looking, wrong, and reported nowhere. `IdRemap` is the only bridge, and `Scene::delete_selected` already carries the `Selection` across it; the trap is for anything else that caches ids (a file format, a second object, an id embedded in a UI label).

### 3.6 Test Placement
Tests live in each file's bottom `mod tests`, and pure-module tests never open a window or a GPU context. Put new *logic* in a pure module and test it there. Put new *wiring* in `renderer.rs` and test it the way `hotkey_for` and `drag_action_label` already are: as a free pure function the seam calls, asserted directly.

## 5. Conventions & Invariants
- **Coordinate Space:** Right-handed, Y-up. Front faces wind counter-clockwise (`FrontFace::Ccw`, back-face culling on).
- **Flat Shading:** One normal per face (Newell's method in `face_normal`). Render vertices are un-welded, and `RenderMesh::vertex_faces` records which face each one came from. Faces are triangulated as fans (must remain convex).
- **Component IDs:** `VertexId`, `HalfEdgeId`, `FaceId` are `usize` newtypes indexing the `Vec`s in `HalfEdgeMesh`. `EdgeId` is an undirected pair of vertex indices (smaller first), so both half-edges of an edge produce the identical id.
- **Storage: append-only, except `delete_faces`.** Extrude, bevel and loop cut only ever *move and rewire in place and append*, which is what makes a bare `usize` a stable reference; they must never `swap_remove` or truncate. Delete is the one edit that cannot be done that way, and the decision taken is **rebuild and dense-pack, not tombstones or generational ids**: `delete_faces` builds fresh `Vec`s from the records that survive and returns an `IdRemap` describing where every component went (`None` = gone), so no stale id is ever dereferenced - it is *translated* or dropped. Tombstones were rejected because history already snapshots whole meshes, which forfeits the memory a tombstone saves while keeping its cost: holes in the arrays that `generate_render_buffers`, `edges()` and every range check would each have to learn to skip. Dense packing keeps those honest and keeps `Scene::restore`'s range clip (`v.0 < vertex_count`) correct. The price is that ids above a retired record name their *neighbour*, which is silent - hence the remap, and §3.5.
- **Validate After Every Edit:** `HalfEdgeMesh::validate() -> Result<(), TopologyErrors>` reports every violated invariant in one pass - the list is in §7's illegal-geometry bullet. `mesh_edit.rs` makes this structural rather than advisory: each primitive refuses a bad argument, rewires a **clone**, `validate()`s the clone, and installs it only if it holds - so a refused edit leaves the document byte-identical and nothing has to be undone. Checking the *candidate* rather than the input is also what blocks editing a mesh that already arrived broken. Five production paths reach it, all through `Scene`: the extrude drag quartet, `insert_edge_loop` on Shift+L, `bevel_selected_edge` on Shift+B, `delete_selected` on Del, and `fill_holes`.
- **Edit primitives are all-or-nothing and total:** every fallible read on the edit path is `Option`-safe (`destination_of`, `edge_id_of`) instead of the `expect`-based queries in `mesh.rs`, because an edit is how bad topology gets *reported* and must describe damage rather than panic on it. `add_vertex` may leave a vertex unclaimed mid-sequence - legal, since nothing validates until the candidate is checked, and how `append_face` builds a mesh from nothing.
- **Edits invalidate the `EdgeId` they consumed** - see §3.5 for why that is silent and what to do. Append-only edits leave every other id valid forever; `delete_selected` is the exception that renumbers, and it answers for all three component kinds through `IdRemap` rather than leaving callers to guess. `SplitEdge` returns the replacement `vertex`, `edges` and `half_edge`; `EdgeLoopCut` and `Beveled` return the ids each operation created.
- **Half-edge record shape:** `HalfEdge { origin, twin, next, prev, face }` - the opposite half-edge is `twin`, not `opposite`, and `twin`, `next`, `prev` and `face` are all `Option` (a boundary edge has no twin). `MeshVertex { position, half_edge }` stores one outgoing half-edge, also `Option`. There is no destination field; use `half_edge_destination()`.
- **Screen-Space Tolerances:** Picking and gizmo arm tolerances are measured in screen pixels (`VERTEX_PICK_RADIUS_PIXELS`, `EDGE_PICK_RADIUS_PIXELS`, `GIZMO_PICK_TOLERANCE_PIXELS`) via `world_per_pixel()`, maintaining consistent feel at any zoom level. Components behind nearer faces are occluded; gizmo arms bypass depth occlusion (`Always` pass).
- **Selection Semantics:** One selection set per component kind; switching `EditMode` drops other kinds. Plain click replaces selection, Shift+click toggles, and plain click on empty space clears (Maya semantics).
- **Tool Independence:** Active tool (`Tool::Select`, `Tool::Translate`, `Tool::Rotate`, `Tool::Scale`) is decoupled from `EditMode`. Switching modes preserves tool; switching tools preserves selection.
- **GPU Vertex Layout Sync:** `GpuVertex` (and `CameraUniform`) live in `src/render_types.rs` and derive `bytemuck::Pod`/`Zeroable`. One struct serves every pass - `position` plus `normal`, which carries a surface normal for shaded faces but a screen-pixel offset for billboarded vertex dots - so it must stay strictly in sync with the single `wgpu::VertexBufferLayout` and the `@location(n)` declarations in `shader.wgsl`. `overlay.rs` exposes it as `OverlayVertex` via a type alias; do not reintroduce a second vertex struct.

## 7. Status (update at the end of every task)
Write what the app *does now*, not how it got here. The per-iteration narrative lives in `git log`; do not re-grow a build history here - it is the first thing to go stale and the last thing a model needs. **Mechanics belong in the doc comments of the function that implements them**: `mesh_edit.rs` and `scene.rs` carry ~630 lines of doc comments explaining *why* each operation is built as it is. This section states the decision and the invariant, then names the file.
- **Working (run-tested):**
  - Flat-shaded cube from the half-edge mesh with Newell normals. Maya navigation: `Alt`+LMB orbit, `Alt`+MMB pan, `Alt`+RMB and wheel zoom.
  - Selection: viewport click casts an NDC ray, Shift+click toggles, empty click clears; the marking pie menu (hold RMB without Alt, or Spacebar, flick and release) switches `EditMode`; `F9`/`F10`/`F11` pick vertex/edge/face and `F8` returns to the mode last used via `Scene::last_component_mode` - entering Object mode must never overwrite it, or toggling twice drifts.
  - Overlays: selected faces warm orange, selected object green, wireframe edges with depth bias (cyan when selected), vertex square dots blue / bright yellow.
  - **Menu bar** (`menu.rs` holds the table, `ui.rs` draws it): every command in Maya's standard modelling menus is listed, so the bar doubles as an honest Maya checklist that gets noticed rather than going stale. Two kinds of grey, two tooltips: no implementation behind it, or a command that exists but does not apply right now. Availability is assembled from `UiContext` and never recomputed in the menu - a menu that decides for itself is a second opinion, and the second opinion is the one that offers a command the viewport then refuses.
  - **One command, one implementation, up to four routes** - hotkey, menu row, Tools panel button, pie flick - all landing in the same `State` method. That is what keeps the bar from drifting and what a new command must respect: add a `menu::Command` variant, its row, the method - **and its entry in `menu::ALL_COMMANDS`**, a list spelled out by hand on purpose so the two drift tests have something to compare rows against. Forgetting it is caught, by `no_menu_row_offers_a_command_the_enum_no_longer_has` rather than by review.
  - **Select commands**, Maya's chords: `Ctrl+A` All, `Ctrl+Shift+A` None, `Ctrl+Shift+I` Invert, each acting on the mode in use. **All three are deliberately outside history** - a `DocumentSnapshot` carries selection, so recording them would spend 64 undo slots on clicks, and Maya's habit of undoing selections is a standing complaint. All and Invert work against the *live* mesh, so ids that outlived an edit are shed rather than carried. `Ctrl+A` is the one knowingly-stolen chord (Maya's Attribute Editor); renegotiate it if an attribute system lands.
  - **Transform gizmo** (`W`/`E`/`R`): one constant-pixel-size handle at the selection pivot - three arms, plus three rings when `E` is up, each through the arm tips and lying in the plane its own drag measures - hover highlight, drawn and picked on the same `Tool::has_gizmo()` predicate, release commits, Escape restores. A whole drag is one history step; a press-and-release that moved nothing records none. **Move** offsets along the grabbed arm; **Scale** divides travel by the selection's own `span_along` that arm, so the rate is a property of the geometry (a drag that doubles a wall doubles a face) and is floored at `MIN_SCALE_FACTOR` because a factor through zero inverts every face it touches and `validate` cannot see it; **Rotate** sweeps the bearing across the ring's plane. All three rebuild from the grab snapshot, so the cursor is a position rather than a delta - back it up and the geometry comes back - and `DragState::restore` is therefore the tool's *identity* (no travel, no turn, unit stretch) rather than an inversion of the steps taken.
  - **Reference system** (`X`, menu, or the "Gizmo:" row): `Space::World` or `Space::Component`, the latter oriented by the selected geometry - a face's normal, **an edge's averaged adjacent-face normal** (not the edge's own direction: pulling Z should lift an edge out *between* the faces meeting at it), or a vertex's averaged faces - falling back to World when the selection has no single direction. There is **no `Space::Object`** and there must not be one before an object transform exists: the document is one mesh with vertices in world coordinates, so an object frame would be numerically World while implying a hierarchy the app lacks. `DragState` stores the `Frame` it was grabbed with, so switching space mid-drag cannot lurch geometry already in flight, and draw, hover-pick and drag all read that one frame.
  - **Extrude** (`Shift+E` **arms a drag**; the mouse sets how far the faces travel, click settles the depth, Escape abandons and restores): a wall grows behind every edge of the selection nothing else bounds, and the axis grabbed is the axis the geometry moves because depth is read along `gizmo::Frame::from_axis(pivot, normal)` rather than a world axis. Faces travel along the average of their own normals, **recomputed from the live mesh on every arm - no direction is ever remembered**, because a cached one makes a picked wall slide sideways through its own prism. Normals that cancel (two opposite faces) are refused, never pushed by a zero vector. **The faces that moved stay selected, not the walls** - see the selection rule at the end of this section. Refusals reach the command echo with their reason. `UiContext.extruding` keeps panel and viewport telling one story, and `CameraController::is_navigating()` gates cursor tracking so orbiting mid-gesture is not banked as depth; `DragAnchor::advance` clamps each step so a flick cannot fling geometry.
  - **Insert Edge Loop** (`Shift+L`, or menu/panel): takes the **one** edge selected in Edge mode; `mesh_edit::edge_loop_crossings` walks the ring and each crossing is opened with `split_edge` then cut with `split_face`. Composition *is* the design: every step validates its own result, so the ring lands whole or nothing does. **Quads only, and the ring stops where the quads stop** - "the edge opposite this one" is not a thing an n-gon has - and the cut is laid down as far as it can be measured so **where it stopped is visible in the mesh** rather than the whole tool refusing; only a ring that cannot even start is refused, since cutting nothing is indistinguishable from a dead key. The new ring stays selected so a second press cuts from under the cursor. Two edges selected is refused with a reason: they can name the same ring, and the second would arrive to find its edges already split - and the edges the ring passed through are dead ids afterwards, so take ids from the returned `EdgeLoopCut` (§3.5).
  - **Bevel** (`Shift+B`, or menu/panel): the **one** edge selected in Edge mode. `mesh_edit::bevel_edge(edge, amount)` fills the gap between the two faces it bounded with a flat facet, taking a cube from 8/12/6 to **10/15/7** vertices/edges/faces and leaving pentagons where the faces met the edge. `amount` (`BEVEL_AMOUNT`) is a **fraction of each adjoining edge, not a distance**, so one setting reads the same on a unit cube and a hundred-unit terrain; past about a third the facet starts eating the faces either side. **No deletion was needed** - appended facet, relocated endpoints - which is why §5's storage decision waited for delete. Refused with reasons: a boundary edge (a rim around an opening is a different construction), and any corner of degree four or higher, which would strand vertices. **Selection goes to the facet's four edges**, deliberately breaking extrude's keep-what-you-picked rule because the `EdgeId` handed in resolves to the wrong edge afterwards (§3.5).
  - **Delete** (`Del`, or menu/panel): retires what is selected and leaves an **opening** - Maya's `Del`, and the first operation that removes anything. Faces go directly; a selected corner takes every face attached to it (a corner cannot be lifted out of a shell without them, and this is Maya's behaviour); **Edge mode refuses**, because Maya's `Del` on an edge *merges* the two faces it joins rather than removing anything - a separate construction, which is why `menu.rs` keeps "Remove" as its own greyed row beside a live "Delete Component". `mesh_edit::delete_faces(faces)` rebuilds and dense-packs per §5, returning `Deleted` with counts and the `IdRemap`; `Scene::delete_selected` then carries the selection across the renumber, re-checking surviving **edges** against the rebuilt mesh on top of the remap - a remap can report where two corners went without reporting that any face still runs between them. `DeleteCommit` echoes counts only, never ids: the numbers a user was shown would otherwise name different faces after the rebuild. **An opening is legal topology** - `validate` has always accepted boundary edges, which is what makes a hole a *result* rather than an error - so a deleted face leaves a rim for Fill Hole to close.
  - **Fill Hole** (menu/panel; Maya binds no key and neither did we): caps **every** opening in the mesh in one undo step. Not selection-driven - the only edit whose availability is a property of the *mesh* (`can_fill_holes` is one `boundary_edges()` scan), so it is live in Object mode with nothing held, and the echo counts because "Filled 2 openings" is the warning when the mesh had more holes than the user meant to touch. `mesh_edit::boundary_rims()` chains rim half-edges **corner to corner** - walking `next` circles the neighbour face that owns the boundary edge, and the vertex fan breaks at a boundary by definition, so neither traces the hole. The cap takes the rim's corners **reversed**, which is the whole trick: it is the one cyclic order that runs against every neighbour along the shared edge, so `append_face` twins the cap *on* rather than laying a second skin, and the cap wears the normal the missing face had. `validate` cannot be relied on for that - a wrongly wound cap twins correctly - so `filling_an_open_box_grows_the_face_that_was_left_off` requires the cap to reproduce the missing face's corner loop and asserts its normal points out. Two openings meeting at a single **corner** - a pinch - are both closed, **one cap each**: `rim_continuation` resolves the shared corner by the **sharpest left turn** about the arriving face's normal, which always picks the nearer rim and so cannot cross into the neighbouring hole. Refusing that case was the earlier, wrong instinct - a pinch reaches the app from an imported file, where a fill that quits cannot be coaxed - and `each_cap_of_a_pinch_covers_its_own_hole_and_faces_the_way_the_plate_does` holds the line on the shape of each cap, not merely the count. Filling **appends**, so unlike delete it needs no `IdRemap` and the selection is left untouched - but a delete-then-fill round trip restores the shape and *not* the numbers, which `deleting_then_filling_gives_the_solid_back_but_not_its_numbers` pins so nobody calls that pair a no-op.

What that buys specifically: `hotkey_for` / `drag_action_label` / `DragAnchor` are tested as free functions with no window; the panel and menu are tested frame-level by driving `UiState::draw` through egui with synthetic input; `HistoryStack<T>` semantics are tested with `T = i32`; `menu.rs` is tested as a table. Every refusal test asserts the mesh is `PartialEq`-identical afterwards, which is what makes "changes nothing" a tested property rather than a promise.
  - `Scene::restore` re-clips a restored selection through `retain_mode` plus live vertex/face id bounds, so undo can never resurrect a component kind the current mode cannot hold. `HalfEdgeMesh` and `Selection` derive `Clone + PartialEq` (plus `Debug`/`Eq` where meaningful) to support snapshotting and no-op detection.
  - Topology safety net: `validate()` walks every invariant in one linear pass and returns them all as `TopologyErrors` rather than the first, and its tests break the cube deliberately, one per invariant, asserting the failure is *named* rather than merely present. The sharpest: two faces over the same corners running the ring *backwards* share no directed edge and every twin links up, so only `check_faces_are_distinct` sees the overlap. Ids resolve into plain `Option<usize>` before any pass, so a mesh naming a nonexistent component is described instead of panicking inside a query while being diagnosed.

  - Undo / Redo: `Ctrl+Z`, `Ctrl+Y`, `Ctrl+Shift+Z`. Restores geometry and selection, never `EditMode` or `Tool`. Panel buttons name the action each would perform and grey out when the queue runs dry.
- **Illegal geometry - what `validate` refuses, and what it deliberately does not.** Refused: two faces over the same corners, a vertex attached to nothing, zero-area faces, duplicated directed edges, and a fan that falls into two pieces (`check_faces_are_distinct`, `check_vertices`). **A degree-one spike is *not* refused, on purpose** - `check_vertices` only asks that a vertex start some edge. It is unreachable today for a provable reason: delete is **face-based**, a surviving corner is claimed by some face, and any face claiming it contributes **two** incident edges. It becomes reachable the day edge-level removal lands (Maya's "Remove"), and only then does that pass belong in `TopologyScan`, with a test that builds the shape deliberately. Never a check that silently rewrites the mesh. Also uncapturable topologically: a miswound *boundary* face, and faces crossing in space without sharing corners, since `MIN_FACE_AREA` judges area, not intersection.

An operation that *replaces* components has no surviving id to hold and must state its own hand-off rather than copying this - bevel does, above.
